# Agent Instructions

This repository is First Mile Manager's help centre, help.firstmilemanager.co.uk: public and indexed from slice 0, with no gate. It is a copy of Stockist's help centre app (`gpl-ajackson/stockist-support-site`) with Stockist's content taken out and First Mile Manager's put in, decided on `gpl-ajackson/firstmilemanager#56` and built by help#1. It never names Stockist to a reader at an FMM-only Operator. Plans and specs for First Mile Manager, its help included, live in the main repository, `gpl-ajackson/firstmilemanager`; each spec's `## Help content` section says what help it needs.

Issue numbers in code comments and test names (spec #30, #49, #59 and so on) are the Stockist help centre's, where the app was first built; `stockist#n` there is a Stockist issue. Issues numbered in this repository are written `help#n`, and the main repository's `fmm#n`.

## Agent skills

### Issue tracker

GitHub Issues on this repository for the help centre itself; the main repository's issues for specs. See `docs/agents/issue-tracker.md`.

### Triage labels

Canonical 5-role vocabulary. See `docs/agents/triage-labels.md`.

### Domain docs

The domain language is the main repository's `GLOSSARY.md` (in `gpl-ajackson/firstmilemanager`). Articles and code here use exactly its terms; a word on its "avoid" list appears only to say what the right term is. Help-centre terms (Article, Article Name, Audience Tier and so on) are in this repository's `GLOSSARY.md`, and this repository's decisions are in `docs/adr/`.

### Help content

The main repository keeps this site in step with every change it builds. Its side of the rule is `docs/agents/help-content.md` in that repository: one help pull request per spec (or per change with no spec), linking its main-repository pull request and merged straight after it, and a main-repository pull request with no help says `No help changes: <reason>`. This site's side is ADR-0003: a Change Summary in the Next Release folder when the change is news to readers, and a help change with no main-repository pull request says `Help only: <reason>`.

### Writing help

Every Article and Glossary Entry is drafted by the Style Guide (`docs/writing/style-guide.md`) and its type's Article Template (`docs/writing/templates/`, one per Article Type plus `glossary-entry.md`). Before writing a Glossary Entry, look up the term in `content/term-status.yaml`: only a Published term gets one, and its home Product Area says which help pull request writes it.

### Brand

First Mile Manager's brand files and rules are in `brand/`, copied from the marketing repository's `brand/` folder (`gpl-ajackson/firstmilemanager-marketing`), where AJ approves any change first. A courier's branded help centre for its clients never uses them.

## Building and checking

The help centre is a Laravel 13 app on PHP 8.4 with Postgres and Meilisearch, plain Blade and CSS (no front-end build step, no third-party script, no cookie). The content folder `content/` is the only source of Articles; `php artisan help:rebuild` rebuilds the database copy and the search index from it. A merge to `main` deploys once every check passes, and the deploy runs `php artisan optimize` (which also works out the asset fingerprints once, `help:cache-assets`), migrates, then runs `help:rebuild`: `docs/deploying.md` says how a deploy works, and `deploy/forge-deploy.sh` is Forge's deploy script. Readers arrive only through Cloudflare: `config/trustedproxy.php` lists Cloudflare's addresses so `$request->ip()` is the reader's (the vote and Search limits key on it), and the server must accept web traffic only from those addresses.

```sh
composer setup                       # install, .env, key, diagram tool, migrate, help:rebuild
php artisan serve                    # http://localhost:8000/articles/<name>
php artisan help:rebuild             # rebuild from content/ and pictures/ (--content=, --pictures= for others)
composer lint                        # Pint (composer lint:check in CI)
composer types:check                 # PHPStan, level 7 with Larastan
php artisan test                     # Pest, on Postgres (phpunit.xml: host pgsql, database testing) and Meilisearch
php artisan help:launch-checks --main-project=../firstmilemanager --marketing-site=../firstmilemanager-marketing   # the automated Launch Checks (CI adds --pages for checks 7, 8 and 11)
php artisan help:glossary-check --main-project=../firstmilemanager  # the Glossary Check alone, as the weekly run does (--post-to=<owner/repo> posts it)
php artisan help:release-check --main-project=../firstmilemanager   # before an FMM Release: changes since origin/demo with their help, the draft Release Note, and the Launch Checks with every Picture retaken
```

- Search runs on Meilisearch v1.52.4 (`MEILISEARCH_HOST`, `MEILISEARCH_KEY`, `MEILISEARCH_INDEX` in `.env`; `config/help.php` "search"). The rebuild and the tests need a running instance: `meilisearch --master-key=<key>` locally (cloud sessions start one on port 7700), `getmeili/meilisearch:v1.52.4` in CI. With none reachable, `help:rebuild` changes nothing and exits 1, and every test that publishes content fails saying so: tests never skip search.
- Search only through `App\Search\SearchService`, naming the caller's `App\Search\Scope` (`Scope::stockistCentre()` in SR1). Nothing else talks to Meilisearch. `search()` and `suggest()` are never recorded; `settle()` is a settled Search: it is recorded as a Search Record and its result links go through the "opened" address (`/searches/<id>/opened/<place>/<address>`), which marks it Opened and redirects. The plain form settles at `/search`. The search box's script shows suggestions from `GET /suggestions` (the last word, from three letters, may be the start of a longer word; everywhere else words are whole) and settles them at `POST /searches` (`settleSuggestions()`) after two seconds idle with three letters or more, or when a suggestion is opened; the form then names that Search in a hidden `search` field so it is recorded once.
- Tests go through the reader's side (spec #30, seam 1): build a fixture content folder with `content()->article(...)` (`tests/Support/FixtureContent.php`), `publish()` it through `help:rebuild`, then request pages. Assert on what a reader sees, never on the database copy.
- Layout tests (`tests/Support/BrowserLayout.php`) lay a page out in headless Chromium through Playwright, which Node finds on `NODE_PATH` (pre-installed in cloud sessions; CI installs it globally). The site has no root `package.json`; only the rebuild's diagram tool has one, in `tools/diagrams`.
- Article page parts follow the Article Templates: write "In short" as the body's `## In short` Section, a Section Name at the end of its heading (`## The location is too small {#too-small}`), and Troubleshooting messages in the header data's `messages`, never in the body; the page builds "What you see", the details row, related articles, the Getting-started step and the Client-tier closing line from the header data.
- Pictures and diagrams: put a Picture under its step on a line of its own as `![](picture:<Picture Name>)`, with no alt text in the Article: the alt text and desk or handheld come from its Picture Recipe, `pictures/<Picture Name>.yaml` beside `pictures/<Picture Name>.png` (ADR-0005). Write a diagram as a ```` ```mermaid ```` block with an `accDescr: <what it shows>` line after its first line; that line is its alt text. `help:rebuild` fails on a missing Picture, Recipe or alt text, and on a diagram Mermaid can't read. It sizes Pictures and draws diagrams (with `tools/diagrams`, pinned Mermaid and Playwright: `npm ci --prefix tools/diagrams`, and the `gd` PHP extension) into `storage/app/pictures`, served at `/pictures/<fingerprint>/...` and cached for a year; no diagram script reaches a page.
- Styles, fonts and images in `public/` are linked through `App\Site\Asset::url()` (`/assets/<fingerprint>/<path>`, cached for a year); never link `/css/...` or `/fonts/...` directly. Every other response tells Cloudflare not to keep it (`App\Site\Http\Middleware\PagesNotCached`), so Page View Counts stay true.
- Link other help by name, never by address: `[words](article:<name>)`, `[words](article:<name>#<section>)`, `[words](#<section>)` for this Article's own Section, and `[words](term:<term>)` for a Glossary Entry (a staff page gets `/glossary/<term>`, a Client-tier page `/client-glossary/<term>`). `[](article:<name>)` shows the Article's title. A link that leads nowhere shows as plain text and `help:rebuild` lists it with file and line; the Links check fails it.
- Glossary Entries are one file per term: `content/glossary/<term>.md` (Staff) and `content/client-glossary/<term>.md` (Client Glossary), the file name being the term's name in lower case with hyphens (`Stock Container` is `stock-container.md`). Header data: `term` (exactly as `GLOSSARY.md`), `audience_tier`, `where_you_see_it`, `checked_on` (last checked against `GLOSSARY.md`), and optionally `other_names`, `status_values` (`- value:` with `meaning:`, for a status) and `former_names` (a renamed term's old names, whose addresses redirect for good and which readers also see under "Also called"). The body is one or two plain sentences. "Articles that use it" comes from the Articles' `term:` links, never written by hand; only a term's first link on a page is linked. A Client Glossary entry says "your 3PL" and links only to client pages; a staff-only term (Hold Reason, Dock Override) has no client entry. Tests write them with `content()->glossaryEntry(...)` and `->clientGlossaryEntry(...)`.
- Search finds what writers wrote, so write for it: a Troubleshooting Article's `messages` are matched against a pasted message word for word, with each `[Placeholder]` taking the reader's own codes, and put the Article first; a Glossary Entry's term, Other Names and former names put it on top of a Search as a short answer ("Also called bin. In Stockist this is a Location."), and each Other Name finds the term's Articles too, one way only. Pick Other Names that readers really type for the term; an everyday word with other meanings would bring the term into unrelated Searches.
- Examples use the Trentside demo only: an email address, phone number or postcode in the content or a Picture Recipe must be one the main project's demo seeders (`database/seeders`) hold, or our own contact address (`hello@firstmilemanager.co.uk`); Launch Check 6 fails any other.
- Public routes live in `routes/public.php`, in the `public` middleware group, which has no session, cookie or CSRF middleware. Never add a public route to `routes/web.php`.
- Records (`App\Records\Records`) keep Page View Counts, Still Stuck Counts, Search Records (words cleaned to `[email]`, `[phone]`, `[postcode]`, `[number]` by `App\Records\Cleaning`) and Article Feedback votes: by the UK day, never anything about the reader, with obvious bots left out. Every record goes through `Records`, which records nothing until going public (and, from #59, nothing on a Help Preview). Tests turn going public on and send a browser user agent (`A_READER`).
- Keeping periods (rule 11): `help:prune-records` runs every night at 03:30 UK time (the server runs Laravel's scheduler) and first adds every month that is over into monthly totals (numbers only, kept for good), then removes Search Records, votes and Feedback Reasons more than 13 months old and comments more than 6 months old. Page View Counts and Still Stuck Counts are kept for good. At 03:45 `help:delete-old-doesnt-match-issues` deletes every "doesn't match" issue (body starting `DoesntMatchIssue::MARKER_PREFIX`), open or closed, opened before the first day comments are still kept from, comments and all, through GraphQL's `deleteIssue`; GitHub only lets a key whose owner administers the repository delete, so `HELP_GITHUB_ISSUES_TOKEN` must belong to a repository admin (AJ). To delete a comment sooner: `php artisan help:delete-comment <article> [--day=YYYY-MM-DD]` lists that Article's comments with each vote's reference, then `--vote=<reference>` deletes that comment and leaves its vote. What the help centre records and keeps is described in the marketing site's privacy notice (`/privacy` redirects to its help-centre section), so change that notice when a keeping period or a record changes.
- Backups and uptime (#60): `help:back-up-records` runs every night at 04:00 UK time, after the pruning, and backs up every table of records (`App\Records\RecordsBackup::TABLES`; a new table of records belongs there) to the off-server backup store, the `backups` disk (Cloudflare R2, `HELP_BACKUP_*`), as one gzipped JSON lines file, deleting each backup 14 days after it was made. Content is never backed up, since a new server rebuilds it from the repository. `help:restore-records [<day-hhmm>]` restores one into a fresh database, all or nothing. `help:record-uptime` runs at 04:30 and keeps last month's and this month's uptime from Better Stack (`App\Records\UptimeMonitor`, `HELP_UPTIME_*`), which the Help Gaps Report (below) reads with `Records::monthlyUptime()`. All three fail, saying which setting is missing, when the server lacks one. Tests fake the store with `Storage::fake('backups')` and Better Stack with `Http::fake()`. Every scheduled job needs Forge's scheduler (`php artisan schedule:run` every minute). `docs/rebuilding-the-server.md` says how to rebuild the server within a working day.
- The help home and its listings (`App\Site\Http\Controllers\ShowHome`, `ListingPages`: `/roles/<role>`, `/getting-started`, `/areas/<area>`, `/for-your-clients`, `/troubleshooting`) take their Articles from `ContentLibrary` (Published only). Product Areas appear in the order `content/product-areas.yaml` lists the app's menus (areas it doesn't list come after, by name), each only once it has a Published Article. A renamed area keeps its old names in that file as `former_names: [Old Name]`, and `/areas/<old name>` redirects for good. The Role Paths are `App\Content\RolePath`, one per Staff Role (which Team Roles each lists).
- `content/facts.yaml` holds First Mile Manager's name, description, stage and the marketing site's address, copied word for word from the marketing site's `src/data/site.ts` (Launch Check 9 compares them with `site.ts` at main, so change them there first); the header's "Early access" badge, "About Stockist" link and footer come from it, and `help:rebuild` refuses a folder without it. The help centre never states prices, plans or what's coming: it links to the marketing site's pages for them.
- Article Feedback ("Did this answer your question?") is a plain form posted to `/feedback/<name>` (and `/feedback/<name>/reason` after a No). Public pages have no session, so posts carry no CSRF token: `App\Site\Http\Middleware\SameOrigin` refuses any post that didn't come from the help centre's own pages. Votes are rate-limited by a short-lived key in the rate limiter's own cache store (`cache.limiter`, never the database), which `help:forget-rate-limits` clears every five minutes.
- "It doesn't match what I see" votes reach their Article Owner as issues on this repository (`App\IssueDesk\IssueDesk`, run by `php artisan help:doesnt-match-issues`, scheduled every five minutes): one open issue per Article, assigned to its `owner`, later votes added as comments while it is open, a new issue once it is closed. GitHub is reached only through `App\IssueDesk\GitHubIssues` with the server's `HELP_GITHUB_ISSUES_TOKEN`; without it, or while GitHub is down, votes wait for the next run. Tests fake GitHub with `Tests\Support\FakeGitHubIssues::start()` and never call the real API.
- The Help Gaps Report (#67): `help:gaps-report` runs on the hour from 08:00 to 16:00 UK time on the first working day of the month (`App\Reports\ReportMonth`), after the night's `help:record-uptime`, and raises one issue for the Content Owner, labelled `help-gaps-report`, through the issue desk's key (`App\Reports\HelpGapsReport`, from `Records` and `ContentLibrary` only). It links the month's Help Drift Report issue, found by its label and marker: with `--wait-until=16:00` a run that doesn't find it yet raises nothing, and the 16:00 run raises the report without it, saying so. A month's issue, open or closed, is never raised twice; nothing is raised before going public, or for a month before the first record (`Records::countingSince()`). The minimums are constants on `HelpGapsReport`; `php artisan help:gaps-report --month=YYYY-MM --print` prints a month's report without raising it. Readers' words (Searches, comments) and GitHub's (titles, logins) go into an issue only through `App\IssueDesk\IssueText`, so they can't mention anyone or add markup. Tests make records through `Records` with the clock moved, and fake GitHub with `FakeGitHubIssues` (`raised()` adds the Drift Report's issue).
- The site's one script is `public/js/site.js`: plain, no build step, loaded with `defer` on every page. Each part improves markup that already works without script and stores nothing on the device. Add new behaviour there as its own block, and test it in a real browser with `Tests\Support\ReaderBrowser`, which sends every request the page makes through the test's app (`Tests\Support\SearchingReader` does the same for typing in the search box, with the page's clock held so "two seconds idle" is a step).
- Help Previews (#59): every pull request gets one, from `.github/workflows/help-preview.yml`. It is a static copy of the pages readers would see once the pull request merges, written by `php artisan help:preview --into=<folder> [--pull-request=<n>]` (`App\Preview\HelpPreview`: the content rebuilt in a rolled-back transaction, every page asked of the app in-process) and deployed with wrangler to the Cloudflare Pages project as the branch `pr-<n>`. Its link, `https://pr-<n>.fmm-help-previews.pages.dev`, is posted in one comment on the pull request and updated on every push; opening it asks for a Cloudflare Access sign-in (the "Help centre" policy, as for the pre-launch site). Draft Articles show there marked as drafts, listed on the preview's own `/help-preview` page; search and feedback show but do nothing, no script loads, every page says noindex, and nothing is recorded. Closing the pull request deletes its deployments. Secrets (names only): `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `HELP_PREVIEW_PAGES_PROJECT`; without them (a fork, Dependabot) the job passes with a warning and there is no preview. The Launch Checks run on every pull request whether or not anyone opens it. Views check `App\Preview\HelpPreview::isOn()` for anything a preview must draw differently.
- `config/help.php` holds the going-public setting (`help.going_public`, off until launch) and the content folder's path.
- The site's brand files in `public/` (`css/tokens.css`, `fonts/`, the logos and icons) are copies of `brand/`; a test fails when they differ, so copy changes across.
- The automated Launch Checks (`app/LaunchChecks/`, spec #30 seam 2) run over `content/` and a checkout of the main project: `FAIL <file>:<line> [<rule>] <message>` lines fail the build, `REPORT` lines (long sentences, step runs, Articles over guide length) are for the reviewer and never fail it. Article Owners are listed in `content/article-owners.yaml` and Product Areas in `content/product-areas.yaml` (each with its main-project menu label key); Article Templates in `docs/writing/templates/` list their parts in their header data. Tests run them over fixtures with `launchChecks(content()...)->against(mainProject())->templates(templates()...)->run()`.
- Source References go both ways (Launch Check 2): every plan path, `ADR-nnnn` and `fmm#n` in an Article's `source_references` must exist in the main project, and each cited plan (`.junie/plans/...`) or spec (an issue titled "Spec: ..." or with a Help content section) must list the Article back as `/articles/<name>` in its `## Help content` section, where everything listed must exist. Issues are read from GitHub with `FMM_READ_TOKEN` (set it locally to check them; without it the run says they weren't checked). A built feature's plan or spec still listing `new: "<title>"` is reported, and fails at launch: `--at-launch`, or always once going public is on.
- Client-tier Articles never name Stockist in anything a reader sees, since an Operator's clients never meet it (title, summary, messages, words, alt text, web addresses), and link only to Client-tier Articles and the Client Glossary (Launch Check 3).
- Glossary and Words checks (Launch Checks 4 and 5): every `GLOSSARY.md` term has a Term Status in `content/term-status.yaml` (`<term>:` with `status` Published, Internal or Not built yet, its home `product_area`, `ahead: true` where its entries say less than `GLOSSARY.md`, and the `fingerprint` the check prints for its definition); an entry naming a term `GLOSSARY.md` no longer has fails, the rest is reported (a missing Term Status fails with `--at-launch` or once going public). No Article or Glossary Entry uses a `GLOSSARY.md` avoid word or a word the Style Guide bans (its header data's `banned_words`); to name an avoid word as the wrong word, write it alone in quotation marks (Stockist calls a "bin" a location). Quote blocks, the `messages` header, code spans, Other Names, former names, status values and the words in `content/ignored-words.yaml` are skipped. `.github/workflows/glossary-check.yml` runs the Glossary Check every Monday and posts its findings to the Content Owner (`help.content_owner`) on one open issue.
- Every pull request's description links its main-project pull request (`https://github.com/gpl-ajackson/firstmilemanager/pull/<n>`), whose head the Launch Checks then read, or says `Help only: <reason>`; the Launch Checks workflow fails it otherwise.
- Pictures are never taken by hand: write a Picture Recipe as `pictures/<Picture Name>.yaml` and run `php artisan pictures:take <Picture Name>` (ADR-0005). How to write and run a Recipe is in `pictures/README.md`; the tool is `app/Pictures/`. There are no Recipes yet: the tool is copied from Stockist's help centre and still takes Pictures from Stockist alone, and help#3 (slice 1) changes it to take them from a Joint Trentside (Stockist at the version on the demo with First Mile Manager at the change being made). A Stockist release retakes this repository's Pictures too, and waits for its help update when one differs. The tool's own tests take real Pictures and run apart: `php artisan test --testsuite=Pictures` (`.github/workflows/picture-tool.yml` in CI).
- CI (`.github/workflows/ci.yml`) runs Pint, PHPStan, `help:rebuild` over `content/` and Pest on every pull request; `.github/workflows/launch-checks.yml` runs the Launch Checks and posts their findings on the pull request (it needs the `FMM_READ_TOKEN` secret, ticket #32). With `--pages`, as CI runs them, the Launch Checks also open every published page in headless Chromium (Playwright and axe-core pinned in `tools/diagrams`): an axe WCAG 2.2 AA scan, no sideways scrolling at 320px, 390px and 1280px in light and dark, controls at least 44px and the search box 52px (check 7); no cookie or device storage on any page, and a test reader's Search, vote and "Still stuck?" leaving only markers and nothing about the reader in any record (check 8); each page template usable within 3 seconds on slow 4G (check 11; `--speed-at=<address>` also times them at the real address through Cloudflare Access with `CF_ACCESS_CLIENT_ID` and `CF_ACCESS_CLIENT_SECRET`). A new page or template is covered once it is listed in `App\LaunchChecks\Pages\PublishedPages`.
